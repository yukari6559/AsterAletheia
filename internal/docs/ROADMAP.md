# ROADMAP

## 開発ワークフロー（SharpHdl と同型）

- **実装は人手**。エージェントは調査・設計・レビュー・Git 区切り（`.cursor/rules/`）
- **Milestone → Issue（≈1 PR）→ PR 内コミット**。`main` 直の機能／リファクタは避ける
- マージは `gh pr merge --merge` のみ
- 仕様の正 = `internal/docs/`（Git で追跡）、公開利用者向けのみ = `docs/`
- 作業の正 = GitHub Issue／PR
- 詳細正本: [dev-workflow](dev-workflow.md)

## マイルストーン

### M0 — 設計凍結（現フェーズ）

- 8 スコープの役割・責務境界を `internal/docs/` に固定する（[VISION](VISION.md)、[scopes/](scopes/)）
- 共通語彙を [GLOSSARY](GLOSSARY.md) に固定する
- 設計判断を [DECISIONS](DECISIONS.md) に残す
- SharpHdl 同型の開発ルールを設置する

**成功条件:** 各スコープの入力・保証・出力が文書として並立し、スコープ間で用語の意味が食い違わないこと

### M1 以降 — 研究フェーズから切り出す

下の研究フェーズを、レビュー可能な大きさのマイルストーンに切り出す。切り出す前に、技術選定をどう記録するかを決める。  
決めたら本ファイルにマイルストーンとして追記し、GitHub Milestone を作る。

## 研究フェーズ（骨格）

各フェーズは、前のフェーズの体系を壊さずに **主張できる範囲を広げる** ように並べる。初期フェーズの信号源は信頼の根拠が弱く不確かさも大きいが、それを正直に刻印する限り体系は最初から正しく動き、型が主張できる範囲を自動で制限する（[D-06](DECISIONS.md)）。

| フェーズ | 目的 | 主に広がるスコープ | 主な機材ファミリー | 完了の姿 |
|----------|------|--------------------|--------------------|----------|
| **Phase 0** 基盤 | 事象・観測者・不確かさ・信頼の根拠、観測セッション、系譜グラフ、観測の型、モジュール契約を定め、**仮想ノードだけで** 起点から Claim までを端から端まで通す（[D-14](DECISIONS.md)） | S1 / S2 / S4 / S5 / S6 | 全ファミリーの模擬 | 模擬データから、証明木付きの（模擬と明示された）Claim が出て、自動査読を通る |
| **Phase 1** 単一ノード・光学 | 実在の信号源で、変光星の測光や移動天体（流星・人工衛星）の検出を行い、校正から位置決定・光度曲線までの「証明付き解析」を開通する | S2 / S3 / S5 / S6 | 測定カメラ、全天観測、気象観測 | 現実の事象について、測定 Claim と同定 Claim が出る |
| **Phase 2** マルチモーダル | 電波を加え、異分野のストリームを一つの観測セッションに束ねる。光学で火球を検知したら電波の循環バッファを保護する、といったクロスモーダル・トリガーを実証する | S3 / S4 / S5 | 電波観測 | 一つの事象について、光学と電波の Claim が同じ時間軸で並ぶ |
| **Phase 3** 高精度な信頼起点と多点統合 | 公開され検証可能な設計の時刻基準で時刻の不確かさを縮め、小惑星による恒星食（掩蔽）など高い時刻精度を要求する主張と、複数地点の統合を可能にする | S2 / S7 | 時刻基準（公開設計）、移動観測キット | 多点の Claim から合成 Claim が出る |
| **Phase 4** 自律化と地球規模網 | 機材の安全制御を含む自律運用と、世界中のノードへの観測リクエスト配信、検証済み Claim の合成によるオープンサイエンス基盤を公開する | S3 / S7 / S8 | 全ファミリー | 第三者が追試し、Claim を積み上げられる |

時刻基準は最重要だからこそ、Phase 0 から概念の中心にある。Phase 3 で変わるのは時刻の扱いではなく精度であり、時刻モジュールは全機材で共通なので、その改善は全ファミリーの主張できる範囲を同時に広げる（[D-18](DECISIONS.md)）。

フェーズは研究の順序であり、実装技術を定めない。
